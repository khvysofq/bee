# ADR-0004 原始抓取存档：内容寻址不可变存储（本地 FS 起步，接口化，可换 S3）

**状态**：已定稿（P0-1，2026-10-26；同日按 DAW-33 评审修订）｜**决策人**：CTO

## 背景

「原始抓取内容不可变存档」是可信度的物理基础（红线 5）：简报上的每个数字都要能点回
抓取当时的确切原文。页面会更新、链接会失效 —— 必须自己持有原文快照。

## 决策

- 抓取响应本体写入**内容寻址存储**：路径 `raw/YYYY/MM/DD/<sha256>.<ext>`，文件名即内容指纹。
- 数据库 `raw_fetch` 行登记元数据（URL、时间、HTTP 状态、sha256、存储键），并在其上
  **硬禁 UPDATE/DELETE**（触发器）。
- 存储访问走一个极小的接口（`store.put(bytes) → ref` / `store.get(ref)`），v1 实现是本地目录
  （`RAW_STORE_DIR`，默认 `./data/raw-store`），生产替换为 S3 兼容实现即可，不动调用方。

## 为什么

- 内容寻址天然去重（同页面一天抓两次、内容没变 → 一个文件两行登记）；
  不可变由命名结构保证 —— 没有任何进程有「改存档」的路径。
- 内容放文件系统而不是 PG blob：库保持轻（dump/备份小），页面 HTML 几百 KB 也不影响查询内存；
  S3 迁移只需换接口实现。
- 同 URL 新内容 = 新 sha = 新文件 + 新登记行，历史版本全部保留 —— 这正是「变更留痕，可回看历史版本」。

## 弃了什么

- **PG 大对象/bytea 存原文**：v1 量级其实可行，但备份体积、内存与 S3 迁移路径都不占优。
- **git/LFS 存档**：语义错位（版本控制是给人改文件用的），鉴权/生命周期管理也不在点上。
- **IPFS**：概念契合但运维与工具链复杂度高，收益为零。
- **不留存原文、只存 URL**：直接违反红线 —— 来源一改版，所有溯源链归零。

## 修订（DAW-33 评审，2026-10-26）：内容身份与抓取登记分离为两表

原决策把「内容身份」与「抓取事件」都压在 raw_fetch 一行上。评审指出这挡住了两类合法写入：

同内容多入口抓取（同页面两个 URL、镜像站）与修正/回放场景的重新登记。
拆分为：

- `raw_content`：**内容对象表**，主键即 sha256 —— 同内容全库一行；`content_ref`（存储键）首次归档时确定，
  之后以首见作数（内容寻址的「同 sha 同文件」从约定升级为键约束）。
- `raw_fetch`：**抓取事件登记**，一行一次抓取，指向 raw_content —— 同内容抓 N 次 = N 行登记，
  去重只发生在内容层；修正链（price_observation.revision + superseded_by_id）因此不会被内容唯一键挡住。

写入顺序成为硬约束：先 raw_content 后 raw_fetch（外键），管线侧由
`registerRawFetch`（packages/pipeline/src/ledger.ts）封装，返回 `contentExisted` 供调用方决定是否写文件。
迁移 0001 执行（含从旧 raw_fetch 的内容回填）；本 ADR 其余决策不变。

## 影响

- 备份 = `pg_dump` + raw-store 目录（内容寻址无重命名风险，rsync 即可）。
- 溯源查看器（P0-4）：`/raw/{fetchId}` 从登记行取 ref 读原文渲染。
