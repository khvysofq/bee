# ADR-0005 调度与队列：pg-boss（同一 Postgres，零新增基础设施）

**状态**：已定稿（P0-1，2026-10-26；P0-3 落地装配）｜**决策人**：CTO

## 背景

v1 管线节奏：每来源每天 1–2 次抓取，错峰、限速、失败重试；每日一次校验/聚合/发布编排；
异常时人工触发回放。量级小，但**每一步必须可见、可审计、可恢复**（台账化）。

## 决策

- **pg-boss v10** 作为调度与队列，运行在业务同一个 Postgres 上。
- 每个来源一个定时任务（由 `source` 表的频率/限速/时段推导出错峰的 cron），一个 worker 进程消费；
  业务语义（哪个来源、哪个 run、什么结果）一律写**我们自己的台账**（`pipeline_run` / `pipeline_step`），
  pg-boss 只负责「何时叫醒、失败重投」。
- LLM/HTTP 之外的每类作业超时与重试策略在任务定义处显式声明，不使用默认值。

## 为什么

- 队列即数据库：没有第二个有状态服务，没有 Redis；运维面 = 一台 PG。
- 任务的持久化、重试、退避是 pg-boss 职责边界清晰的部分；与「台账不撒谎」原则互补
  （pg-boss 的状态只回答调度问题，业务事实以我们的台账为准）。

## 弃了什么

- **node-cron / 系统 cron**：无持久化、无重试、重启即丢语义；错峰来源级管理全要手写。
- **Redis + BullMQ**：成熟，但为一个每天几百个 job 的系统引入第二个有状态服务不成立。
- **Temporal / 工作流引擎**：durable workflow 的正统答案，但部署面与学习面远超 v1 需要；
  P0-1 的 step 台账 + P0-3 的实现已把「重放」做在数据模型里，不依赖引擎。量大后再议。
- **Airflow / Prefect / Dagster**：数据团队编排栈，Python + 独立服务 + UI，与 TS 单库策略冲突，
  对日频小管线是高射炮打蚊子。
- **GitHub Actions 定时工作流**：时间抖动大、secrets 扩散面大、采集出口不受控，适合 CI 不适合数据产品运行时。

## 影响

- P0-3 在 `packages/pipeline` 引入 pg-boss 并装配 worker；本骨架已把台账 helper 备好。
- 单 worker 进程即可承载 v1；横向扩展时 pg-boss 提供并发语义，无需改模型。
