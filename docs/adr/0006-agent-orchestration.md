# ADR-0006 Agent 编排：显式 step 台账 + 结构化 LLM 判断（不引入编排框架）

**状态**：已定稿（P0-1，2026-10-26；规则细节属 P0-3 输入）｜**决策人**：CTO

## 背景

运行方式已定：采集/校验/异常隔离全自动 Agent 化，人只出现在异常队列与口径决策点。
同时红线要求「可回溯 Agent 的判断依据」「LLM 数字永不进报价表」。**可审计性优先于编排能力**。

## 决策

- 管线 = **确定性的、类型化的 step 序列**（`@bee/core` 的 `PipelineStep` 契约），由 worker 顺序驱动；
  Agent 不是管线的「驾驶员」，是若干个**被调用的判断点**。
- LLM 判断一律走：结构化输出（zod 校验）→ `agent_invocation` 全量留痕（模型/prompt 版本/输入/输出/耗时）
  → 结论落 `validation_result`（check_kind='llm_judgment'，判断依据入 detail）。
- LLM 的四类用途（校验判断、叙事草稿、异常分诊、映射建议）都**只产文字与结论**；
  任何数字要进入报价表，必须能追到 `raw_fetch` 抽取链 —— 管线层强制（P0-3 实现该断言）。
- 人机边界：Agent 拿不准的 → `needs_human` + 异常队列；口径裁决只能人做 → `caliber_decision`。
  Paperclip 平台承担**公司侧运营工作流**（团队/任务/评审），不承担**数据管线运行时**。

## 为什么

- 我们需要的「Agent 编排」其实是**审计协议**：谁（模型/版本）、看了什么（输入引用）、
  说了什么（输出）、据此改了什么（validation_result）。框架的价值（自主循环、工具路由）反而是可审计性的敌人。
- 管线拓扑是线性 + 少量扇出，显式代码比图配置可读、可测、可 diff。
- prompt 与规则演进靠 `prompt_version` / `rules_version` 入台账 —— 每个历史结论都能在原版本上重放。

## 弃了什么

- **LangChain / LangGraph**：抽象层把「实际发生了什么」藏进框架内部，版本与迁移成本高；
  我们没有需要框架的复杂拓扑与自主循环。**结论：不用框架，不排除未来局部借鉴其模式。**
- **各模型厂商内置 Agent 运行时**（工具循环托管）：过程不透明，无法满足留痕红线。
- **用 Paperclip 例行任务跑数据管线**：平台是组织运营平面；数据管线属于产品资产，
  必须随仓库版本化、可本地复现。两者以异常队列为接口衔接（Paperclip 侧消费我们暴露的队列）。
- **MCP/外部 Agent 平台**：同上，运行时外部化即审计链外部化。

## 影响

- P0-3 实现顺序建议：先规则校验（纯确定性）全量跑通，再逐步引入 LLM 判断点；
  每个 LLM 判断点上线时，其 prompt 版本与判定阈值必须随 `rules_version` 入台账。
- 模型供应商中立：调用走标准 SDK + 结构化输出，供应商是配置不是架构。
