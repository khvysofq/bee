# ADR-0002 存储：PostgreSQL 16（单一数据库承担全部职责）

**状态**：已定稿（P0-1，2026-10-26）｜**决策人**：CTO

## 背景

核心资产是强关系的数据：品类/规格/地域/来源/观测/定档/校验留痕层层外键，
还有按 key 的唯一性约束（品类×规格×地域×日期×价类型）、区间 CHECK、append-only 语义。
v1 数据量极小（5 品类 × 核心规格 × 5–8 区域 × 日频 → 每天几千行），但**完整性约束的价值与量无关**。

## 决策

- **PostgreSQL 16 单实例**承担：业务数据、队列（ADR-0005 pg-boss）、P1 问答的向量检索（pgvector，届时加扩展）。
- 金额一律 `numeric(12,2)`（pg numeric 运行时为字符串，禁止隐式 Number()）。
- 结构化元数据（校验依据、运行配置、权重快照）用 `jsonb`；**值字段不用 jsonb** —— 可比性字段必须是列。
- 硬语义交数据库层强制：唯一约束、CHECK、WORM/值不可变触发器（见 data-model.md §不变量）。

## 为什么

- 口径字典与报价 key 的完整性是这个产品的**信任底座**，必须由外键与约束兜住，不能只靠代码自觉。
- 加工指标（全国加权/中位）就是 SQL 的本职；窗口函数支撑环比/周环比的校验查询。
- 队列、向量、全文检索都能用扩展解决，v1 不需要任何第二个有状态组件。

## 弃了什么

- **MySQL**：JSON/数组/分析函数均弱一档；CHECK 与触发器在 8.0 前缺失形成的历史习惯差异；
  无 pg-boss/pgvector 等即插即用生态。
- **MongoDB**：本模型是教科书式关系模型（维度表 + 事实表 + 约束），文档库会把「唯一 key」「不可变」
  这些硬约束全部降级为应用层自觉 —— 与红线冲突。
- **SQLite**：本地开发友好，但 web + worker 双进程并发写 + pg-boss 都不成立；换库成本大于一开始就用 PG。
- **ClickHouse / DuckDB / OLAP 系列**：分析层选型，不是事实层选型；v1 量级在 PG 上做聚合绰绰有余，
  需要时作为下游派生库加，不动主库。
- **TimescaleDB**：日频数据没有 hypertable 需求；它是 PG 扩展，将来真要也是平滑升级路径，不算弃掉。

## 影响

- docker-compose 提供本地 PG；生产单实例起步（ADR-0008）。
- 备份策略 = 每日 `pg_dump` + 原始存档目录快照（存档内容另有内容寻址去重，见 ADR-0004）。
